## Where I needed help

1. **Port clash with no way out.** `npm run demo` died with `Error: listen EADDRINUSE: address already in use 127.0.0.1:8820` and a Node stack trace. The README gives no `--port` option and the script does not print one. Fix: catch EADDRINUSE and print "port 8820 is busy; run `npm run demo -- --port 8830`" (and support it), or at least say in the README which ports it uses.
2. **Becoming the buyer.** The README's "Switch people from the top-right menu (local preview only)" does not apply to `npm run demo`; the menu there has only "Your profile / Sign out / Disconnect Synthetic demo wallet". The console's "Controls: http://127.0.0.1:8821/" returns bare JSON (`{"account":"delphine.near","accounts":[...]}`) with no hint that `POST /account/<id>` switches. I only got past this by reading the comment at the top of `scripts/demo.ts`, which the brief forbids a judge from doing. Fix: put an account picker in the synthetic wallet dialog (it already says "Review harness"), or at minimum make `GET /` on 8821 return `{"switch":"POST /account/<id>"}` and put the sentence "To act as the buyer: POST http://127.0.0.1:8821/account/buyer.near, then sign out and in" in the README's Try it section.
3. **"The buyer gets a first shift"** (README) -> after "Open your business" the desk says "Nothing is waiting right now". Nothing told the buyer to confirm control, appoint a team, or serve a customer. Fix: either show that checklist on the buyer's desk after a close or soften the README sentence.
4. **"Try a real owner action to see the contract refuse it"** (README) -> as the former owner I found no such button; the old desk URL just says "No such business". Fix: a "Try an owner action (will be refused)" button on the former seller's sale page, or drop the claim from the README.
5. **"Sign in with the demo wallet"** (README) vs console "Signs in as Delphine Marsh" vs dialog "Continue with Synthetic demo wallet". Three names for one thing; harmless but a judge pauses. Also the sale page header reads "BUSINESS CONTRACT ON NEAR TESTNET" while the demo banner says "synthetic wallet and chain"; the page-level label should say synthetic in the demo.
6. **Verifying the live contract.** The README says "read `get_control` / `get_entitlement` on the contract" but not the argument names; `get_entitlement` needs `{"customer": "...", "plan_id": 1}` and I found that from three contract panics. Fix: give the two curl commands verbatim in the README (or have `verify-rehearsal.ts --live` do the reads).
7. **Explorer links.** testnet.nearblocks.io served a Cloudflare bot check in the built-in browser, so the "open the explorer links" proof was not available to me. Not the project's fault, but offering the RPC command as an alternative (see 6) would have covered it.
8. **Settlement stuck?** The customer's "Settle my unit" stayed at "Waiting for the contract to confirm the charge" for as long as I watched. Either the synthetic chain needs a tick I did not trigger, or something is wrong; the page should say which and roughly how long to wait.
9. **README length.** The "Everything in it" list is about 25 bullets of features before "Run it". A judge wants: run it, the one flow to try, what's real on testnet, how to verify. Everything else can be a linked doc.

## What ran on testnet vs simulated

My understanding, from the README and the demo only:

- **Simulated (what I clicked):** everything in `npm run demo`. Banner says "synthetic wallet and chain"; the sign-in dialog says the wallet "is not a real wallet or account"; contract `signalwatch.demo.near` and token `tusd.near` are synthetic; the 30-day history is generated at startup. No NEAR network was contacted by the demo as far as I could tell. The README is clear about this ("runs entirely on your machine with a synthetic wallet and chain").
- **Ran on NEAR testnet (what I verified):** the business-v3 Direct sale on `ledgerline-v3-2.everstreet.testnet` on Nov 6 2026: deploy born-locked (0 access keys, confirmed live), customer buys 100 / uses 20, sale closes with owner -> buyer-v3s2 at generation 2 (confirmed live via `get_control`), customer's 80 unchanged at close and 78 free / 22 consumed now (confirmed live via `get_entitlement`), three of its transactions confirmed as SuccessValue via public RPC. The README also claims Gated sale, lost-purchase recovery and failed-payout recovery on testnet with their own evidence files, and earlier v1 (OpenSeat) and v2 (pottery studio) sales; I did not check those.
- **Ran on a local NEAR node (not testnet):** the payout gas sweep and the close-mid-refund case (`v3-sandbox-payouts.txt`).
- **Unit tests only:** the 92 attack tests and the 195-test contract suite; the four "Reproduce locally" vitest rows.
- **Left me unsure:** (a) the demo's "BUSINESS CONTRACT ON NEAR TESTNET" page header inside a synthetic run; (b) whether the same app code path I clicked in the demo is what produced the testnet records (README says "through Everstreet's own routes" / "the app's normal routes", and the record names the commit, so probably yes, but the demo's contract is `signalwatch.demo.near` while the testnet one is a Ledgerline, so the Signalwatch sale I did was never run on testnet as such); (c) "a labelled stand-in AI model" means no AI provider was ever called on testnet, which the README says plainly once, but the demo's cost tiles ("scripted-runtime-model", tokens in/out, cents) could make a hurried judge think a model ran; (d) the attack review's "reviewer that had never seen the project" is, per the report's first line, Claude (an AI model), reviewing a project built with Claude. It was given only the contract source and its docs, which is a fair cold read, but "cold reviewer" made me picture a person.

## Would I trust it

Yes, with one reservation. The central claim is held by the contract, not the app, and I could check it from outside: the account has no keys, control is at generation 2 under the buyer, and the customer's units sat untouched through the close and were spent only afterwards; the safety case names what enforces each promise, lists what was tried and refused, and is unusually candid about what stays open (callback gas measured not proven; the app follows the contract rather than enforcing it). The reservation: the "cold" attack review is an AI reviewer from the same toolchain, the app-side refusal I saw was a hidden page rather than a contract error, and the customer's charge never settled in front of me, so the "buyer serves the next request" half is something I read in the record rather than watched.

## Top three changes

1. **Make the buyer reachable without reading source.** An account picker in the synthetic wallet dialog (Delphine / Noah the buyer / Cara the customer), and one README line: "Sign in as the buyer to close the sale, as Cara to use the product afterwards." This cost me a quarter of the session and would stop most judges at the halfway point.
2. **Put the verification commands in the README verbatim**, including the two `curl` RPC reads (`get_control`, `get_entitlement` with `{"customer":..., "plan_id":1}`) and the expected answers, so a judge whose explorer is blocked or rate-limited can still confirm the claim in a minute. Add `--port` to `npm run demo` and name both ports.
3. **Make the demo match the README's three promises, visibly.** After the close: a "Try an owner action (the contract will refuse it)" button for the former seller, a short first-shift list for the buyer, and a settlement that completes (or says why it is waiting). Then cut "Everything in it" to a linked doc so "Try it -> what it proves -> verify" fits on one screen.
