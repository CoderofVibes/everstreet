## 1. Verdicts

**Piece 1, the handover strip: holds, and it is strong.** Every value on the strip traces to a
named field of one of four records that verify offline and against live testnet (code hash, zero
access keys, owner ines-v3s4 at generation 4, cara 78 unused / 22 used all match). The three
closes, the three refusals and the receipts behind them are real testnet transactions; the
"it asked this business who the owner is" line is true of all three (the business contract appears
as an executor in each refusing call's receipts). The things it doesn't know ("Not read") it says.
Two low findings about wording ("Now", and a refusal taken from a later run without saying so).

**Piece 2, revenue by source: holds for what it claims, with a weaker evidence record.** The
classification is conservative (an unread registration is never counted as independent; the
buyer's projection starts from independent uses only), the route is reachable only by the owner
and the buyer of the live deal (anonymous 401, a stranger and a customer 404), and the demo and
synthetic tests pin the behaviour. But the committed testnet record for it carries no block
heights (the script that now writes them was changed after the record was taken, and the record
was not re-taken), `npm run check` is red at this commit because the attack-suite test was not
updated for the new tenth group, and the buyer is shown linked customers' account ids, which the
rest of the sale pages withhold from anyone but the owner.

**Piece 3, the static copy: holds.** Built from the same verified projections the server serves;
every route (landing, proof, docket, the three example pages, an unknown path) renders from
`localhost:8830` with no request leaving the host; any `/api/` read other than the two data files
answers a synthetic 404. Nothing private in the output (no paths, hosts, keys, database content;
only fictional testnet accounts and public explorer links). 1440 and 390 px both fine.

## 2. Findings, most severe first

No high findings.

### M1 · `npm run check` fails at this commit (piece 2's attack-suite case)

- **Where:** `server/test/attack-suite.test.ts:25` expects `r.groups` to have length 9 and `:28`
  expects 8 distinct case groups. `data/evidence/attack-suite.json` (re-recorded in `996001e`)
  has 10 groups and 9 case groups, because "Revenue attribution" was added as group 9 and the
  planted faults moved to group 10.
- **Reproduce:** `npm run check` → `Test Files 1 failed | 306 passed`, the assertion
  `expected [ Array(10) ] to have a length of 9`. (`npx vitest run server/test/attack-suite.test.ts`
  shows the same; `npm run attacks -- --check` itself passes: `OK: 27/27 cases, 5/5 planted`.)
- **Why it matters:** the committed README tells judges that the permission tests "run with
  `npm run check`" and lists `npm run check` as the lint/typecheck/test command. A judge who runs
  it sees red on the very suite the docket advertises. The fix is a two-number test update, but it
  should be done before anything is captured.

### M2 · The linked-revenue testnet record names no block for any checkpoint; the committed script and the committed record disagree

- **Where:** `data/evidence/linked-revenue-testnet.json` checkpoints `start`,
  `registration_paid_by_owner`, `used_once` have `views.control`, `views.entitlement`,
  `views.earlier_customer` and no `views.block`. `scripts/linked-revenue-testnet.ts:96-101` now
  reads a final block per checkpoint (added in `7fa7a32`, with a comment that the first run's
  record carries none), but the record's `header.commit` is `6b72232`, before that change, and it
  was never re-recorded.
- **Reproduce:** `npx tsx scripts/verify-rehearsal.ts data/evidence/linked-revenue-testnet.json`
  → `3 checkpoints at final finality (0 name their block)`. Compare the other four records, which
  each say "each names its block".
- **Why it matters:** the brief calls this piece's testnet run evidence. Without a block the
  `wren 0 → 1 used`, `cara stays 78` and `owner ines` reads cannot be re-read at the moment they
  describe; the `--live` check only confirms the present state happens to match. And a record whose
  format the committed script no longer produces invites the question of which code made it. Either
  re-run the script (one `sponsor_shell`, one purchase, one use: it is cheap) or state on the
  record's consumers that these checkpoints are unpinned. Note the `header.commit` of
  `ledgerline-after-sales-testnet.json` (`7922ace`) is likewise before its own commit of record,
  which is normal; the problem is only the shape mismatch.

### M3 · A buyer in a live deal is shown customers' account ids (question as much as finding)

- **Where:** `server/src/revenueSources.ts:167` returns `linked.accounts[].account`;
  `web/src/pages/UseEconomicsPage.tsx:108-119` renders them. The route
  `/api/sales/:business/economics` (`server/src/app.ts:742`) admits the owner and the live deal's
  buyer (`saleActions.ts:916-919`).
- **Reproduce:** `POST 127.0.0.1:8821/account/buyer.near`, sign in, `GET
  /api/sales/ef8e56e6-ba9f-41bb-b98c-682aefab9def/economics` → 200 with
  `revenue_sources.linked.accounts[0].account = "theo.near"`. The sale page's reading for the same
  buyer gives only totals (`customer_obligations`, `saleActions.ts:1130-1137`), and the docket's
  own case "Former owner reads customer data" treats a customer account appearing in a response as
  a leak.
- **Why it matters:** a buyer is a third party until the close. Naming a linked customer is
  arguably the point (the buyer must be able to see *who* the seller's side is), and the
  `owner_account`/`operator`/`owner_here`/`team_here` reasons name the seller's own accounts. But
  `registration_paid_by_seller` names a real customer (Theo in the demo, Wren on testnet) to
  someone who is not the owner. Decide and state it: either show those as a count ("1 customer
  whose registration the owner paid") or say in the "What's checked" details that linked
  customers are named to the buyer. Marked medium because it cuts against the project's own
  stated rule; downgrade to a decision if that rule was never meant to cover this.

### L1 · Revenue by source values every use at one plan's current price

- **Where:** `server/src/useEconomics.ts:49` takes `plan_id` from the last charged use and `:91`
  its `unit_price`; `revenueSources.ts:155` multiplies each bucket's use count by that one price.
- **Why it matters:** a business with two plans at different prices, or a plan whose price was
  changed, gets a split whose TUSD figures are wrong while the counts are right. The same
  assumption already sits under `books.earned_revenue` (`:148`), so this is inherited, not new,
  but the new card presents the figures as money per bucket. Say "at today's price" or sum per
  plan.

### L2 · "Now" on the strip is a snapshot from before later recorded activity

- **Where:** `RecordedProof.tsx:200` labels the after-sales row "Now"; the row's block
  (276677171, 20:04Z Nov 7) predates `linked-revenue-testnet.json` (22:10Z), which added a
  customer and a 23rd charged use to the same business.
- **Why it matters:** the row's facts are true at its block (and live cara reads still match), but
  "Now" reads as current. "After the last sale" or "At block 276677171" would be exact, and the
  `scripts/ledgerline-after-sales.ts` snapshot has no refresh path other than re-running it.

### L3 · Sale 1's "former owner after the close" comes from a different run, unsaid on the row

- **Where:** `examples.ts:286-295` searches all later steps across all records; sale 1's refusal
  (`75gAQJnF…`, feed-key-v3s3) is in `v3-ext-testnet.json`, about 30 minutes after the close in
  `v3-direct-testnet.json`. The row says "Former owner after the close"; the record path is only
  under "Check these records".
- **Why it matters:** true, but a judge comparing the two explorer timestamps may wonder. One word
  ("in a later run") would close it. Also a question: the search accepts any receiver
  (`x.s.call?.receiver` is not checked against the business or its companions), so a former
  owner's `E_NOT_OWNER` on an unrelated contract would be attributed to this sale. Harmless with
  these records.

### L4 · The static copy's secret check runs only at build time; no test builds it

- **Where:** `scripts/build-proof-site.ts:200` applies `SECRETISH` to the two data files;
  `web/test/proofSite.test.tsx` checks the reads and the 404 override but never the output. The
  bundled `assets/*.js` and `*.css` are not scanned at all (I scanned them by hand: nothing found).
- **Why it matters:** low, because the data files come from projections that already allowlist
  fields. A one-line test that builds into a temp dir and greps the whole output for
  `SECRETISH`, `127.0.0.1`, `C:\`, `/mnt/`, `.db` would pin the "nothing private" claim.

### Questions (not findings)

- `handoversFrom` keys rows by `closed.hash`; two records holding the same close (a resumed run
  re-recorded) would render the sale twice. Is a resumed run ever written as a second record?
- `PAYERS_READ_MAX = 50` pairs (`useEconomics.ts:20`): beyond that, customers fall into
  "Registration not read", which is the honest bucket. Is there a route-level test for it? I
  found only unit tests for the `unchecked` bucket.
- The vite preview configured for port 8830 (`web/vite.proof.config.ts`, `strictPort: true`) was
  already held by another process; the pane's `preview_start` fell to 8831 and vite refused it.
  Not a finding, but a judge following `.claude/launch.json` would hit the same if 8830 is busy.

## 3. What I checked and found sound

**Evidence.** All five records verify offline and with `--live` (`v3-direct`, `v3-ext`, `v3-s4`,
`ledgerline-after-sales`, `linked-revenue`): code hash `H1bHmRMX…TUvw`, 0 access keys, owner
