# 003d v2 amendment: resolving the nine review points

I changed no files, ran no commands, sent no transactions and changed no status. Everything here comes from reading the review, the saved v1 proposal and the source I read for v1. I tested nothing. This amendment **replaces** v1 §3 (Entitlement), §5, §6 (payouts), §7, §9.1–9.2, §11 (ordering), §12 and §14–16 where they conflict. Everything else in v1 stands.

On three points I went further than the review asked:

- **Point 1:** I chose hold-bound slots instead of a fingerprint window.
- **Point 7:** I replaced the ordering rule with a single on-chain counter, because a better composite key would still be fragile.
- **Point 8:** I removed the transferable readiness signature altogether.

The reasons are given in each section.

---

## A. Customer identity, keys, consent and binding uses to holds (points 2, 3, 4 and 1)

### A.1 State that replaces v1's

```rust
reg_seq: u64                                   // business-wide; incremented, never reset or reused

pub struct Entitlement {                       // key (customer, plan_id); fixed size
    reg_id: u64,                               // = ++reg_seq when the record is created
    status: u8,                                // 0 = Shell (sponsored, no rights), 1 = Active
    free: u64, consumed: u64, refunded: u64, purchased: u64,
    purchase_seq: u32,
    hold_seq: u32,                             // highest hold sequence consumed (opened or skipped)
    hold: Hold,                                // fixed; `active` flag
    last_hold: ClosedHold,                     // { seq: u32, charged: u8, slots_root: [u8;32] }
    keys: [KeySlot; 4],
    claim: u128, pending_refunds: u8 /* ≤ 2 */, paused: bool,
    storage_payer: FixedAccount, storage_paid: u128,
}
pub struct KeySlot { state: u8 /*Empty|Active|Revoked*/, epoch: u32, pk: [u8;32],
                     max_hold_units: u8, max_units_per_day: u16, day: u32, held_today: u16 }
pub struct Hold { active: bool, seq: u32, key_slot: u8, key_epoch: u32, pk: [u8;32],
                  units: u8 /* ≤ MAX_HOLD_UNITS = 10 */, opened_at_ms: u64,
                  serve_until_ms: u64, settle_until_ms: u64,
                  used: u16 /* bitmap */, charged: u8, slots: [[u8;32]; 10] }
pub struct FixedAccount { len: u8, bytes: [u8; 64] }   // padded so in-place rewrites never change size
```

**Size (estimated, measured in S1):** Hold about 390 B, keys 184 B, last_hold 37 B, scalars about 150 B, giving a value of about 760 B. Add the key (about 73 B) and trie overhead, and the record is about 0.88 KB. Budget **≤ 1 KB, about 0.01 NEAR at 10¹⁹ yocto/byte** (that price is verified). This is about 1.6× v1's figure, and it buys exact detection of altered replays.

### A.2 Signed messages

Each message is signed by the customer's use-key over `sha256(borsh(tuple))`:

```
HoldAuth = ("business-hold/v1", business, plan_id, customer, reg_id, key_slot, key_epoch,
            hold_seq, units, serve_until_ms)
UseAuth  = ("business-use/v1",  business, plan_id, customer, reg_id, key_slot, key_epoch,
            hold_seq, slot, fingerprint)
```

A use is bound to **exactly one hold**: its registration, key epoch, hold sequence and slot. It has no free-standing expiry; its validity is the life of that hold.

### A.3 Methods (replacing v1 §5.2–5.3)

| Method | Caller | Guards | Effect |
|---|---|---|---|
| `sponsor_shell(customer, plan_id)`, payable | anyone | no record for that key | Creates `Shell`: new `reg_id`, **no keys**, `storage_payer = caller`; measured storage charged. Grants nothing. |
| `ft_on_transfer` msg `buy{plan_id, units, purchase_seq, install?: {slot, pk, max_hold_units, max_units_per_day}}` | token; `sender_id` is the customer, attested by the token | Record exists (Shell or Active); v1's purchase guards; `install.slot` not Active | Units credited; optional key installed with `epoch += 1`; `status = Active`. **One wallet approval** covers purchase and key installation. No storage growth. |
| `install_key(plan_id, slot, pk, max_hold_units, max_units_per_day)`, 1 yocto | **predecessor == customer** | Record exists; slot not Active | `epoch += 1`, Active, policy set |
| `revoke_key(plan_id, slot)`, 1 yocto | customer | slot Active | Revoked, `epoch += 1`. If the active hold was authorized by this slot: `hold.serve_until = min(serve_until, now)`; `settle_until` unchanged. |
| `skip_hold_seq(plan_id)`, 1 yocto | customer | no active hold | `hold_seq += 1`, which invalidates any HoldAuth that was signed but never submitted |
| `set_paused(plan_id, bool)`, 1 yocto | customer | — | While paused, no hold can open |
| `open_hold(customer, plan_id, auth: HoldAuth, sig)` | METERING operator or owner (not payable) | See guards below | See effect below |
| `settle_hold(customer, plan_id, hold_seq, uses: Vec<(slot, fingerprint, sig)>, close)` | METERING operator or owner | Active hold with `hold.seq == hold_seq`; `now ≤ settle_until`; `len ≤ hold.units` | Per use, below. Returns `Vec<{slot, Charged / Already}>`. |
| `release_hold(customer, plan_id, hold_seq)` | operator any time; **anyone** after `settle_until` | active hold with this sequence | Close the hold (below) |
| `unregister(plan_id)`, 1 yocto | customer; or the sponsor if `purchased == 0` and no key was ever installed | `free = 0`, no hold, `claim = 0`, `pending_refunds = 0` | Delete the record; storage returned to `storage_payer` |

**`open_hold` guards:**
- status Active and not paused; no active hold;
- `auth.reg_id == reg_id`;
- `auth.hold_seq == hold_seq + 1`;
- the key slot is Active with `epoch == auth.key_epoch`, and the signature verifies against that slot's `pk`;
- `units ≤ min(slot.max_hold_units, plan.max_hold_units, 10, free)`;
- `now + 60 s ≤ serve_until ≤ now + plan.hold_ttl_ms`;
- the day counter (reset when the UTC day changes): `held_today + units ≤ max_units_per_day`.

**`open_hold` effect:** `hold_seq = auth.hold_seq`; the hold copies `pk`, `key_slot` and `key_epoch`; `settle_until = serve_until + plan.settle_grace_ms`; `free −= units`; `held_today += units`.

**`open_hold` idempotency:** if the active hold already has this sequence with identical (units, serve_until, key), the call returns `Already`. Any other auth for a sequence that has already been used fails with `E_HOLD_SEQ_USED`.

**`settle_hold`, per use:**
- `slot < hold.units`, and the signature verifies against **`hold.pk`** over UseAuth built from the hold's `reg_id`, `key_slot`, `key_epoch` and `hold_seq`.
- Slot unused: record the fingerprint, set the bit, `charged += 1`, charge P.
- Slot used **with the same fingerprint**: `Already`, no charge.
- Slot used **with a different fingerprint**: **panic `E_CONFLICT(slot)`**. The whole batch reverts and nothing is charged.
- `close = true` closes the hold.

**Closing a hold (`release_hold`, or `settle_hold` with `close`):** the remainder `units − charged` returns to `free`; `last_hold = {seq, charged, sha256(ordered (slot, fp) of used slots)}`; the hold is zeroed in place.

### A.4 Invariants

- **U1 (units conserved):** `purchased = free + (hold.active ? hold.units − hold.charged : 0) + consumed + refunded`.
- **U2:** `popcount(hold.used) == hold.charged ≤ hold.units ≤ 10`.
- **U3 (consent chain):** every held unit traces to a HoldAuth signed by an Active key. That key was installed by a transaction from the customer's own account, either `install_key` (predecessor) or a purchase where the FT reports `sender_id`. Every charged unit traces to a UseAuth signed by the same key epoch, for that hold and slot.
- **U4 (no carry-forward):** a UseAuth can be charged only while its exact hold is active and `now ≤ settle_until`. `hold_seq` is monotonic per `reg_id`, and `reg_id` is never reused, so an expired authorization can never be charged in a later hold or a later registration.
- **U5 (bounded lockup):** a unit is locked only by a customer-signed HoldAuth, until at most `auth.serve_until + plan.settle_grace_ms`. The customer chooses that time when signing. Total units held per key per UTC day is at most `max_units_per_day`. `refund_units(free)` is always available.

### A.5 Why this answers points 1–4, critically

- **Point 1.** A bounded fingerprint window per key (W × 40 B per key) could also work. I chose per-hold slots because the bound is structural: at most 10 fingerprints live, and the slot index *is* the request ID within a hold. Altered replays are rejected exactly. Same-request retries return `Already` truthfully. Anything outside the active hold is refused as `E_HOLD_CLOSED`, never charged. The price is about 330 B per entitlement, and a client must reserve a slot before signing.
- **Point 2.** The review proposed either separating sponsorship or a customer-signed installation. A contract can't check an off-chain NEP-413 signature against an account's current access keys: the environment-functions page lists no access-key reader. That is inferred from the docs' function list. So authority comes only from the customer account being the **predecessor**, or from the token attesting `sender_id`. A sponsor pays only for a Shell.
- **Point 3.** `reg_id` comes from a contract counter. Key epochs only increase. Replacing a key never resets `hold_seq` or the slots of the active hold, and the hold carries its own `pk`, so work already authorized under it stays collectible.
- **Point 4 (stated policy on revocation).** Revoking a key ends new service at once (`serve_until` is truncated). Uses the customer already signed in that hold stay settleable until `settle_until`. The contract can't know when a use was signed, so exposure is capped at the hold's remaining units (≤ 10). The deliberate settlement grace means **the contract can't prove a use was served before `serve_until`**; that remains a runtime assertion.

### A.6 Customer experience

- **One wallet approval:** buy plus install key. Use-keys sign HoldAuth and UseAuth silently, within the policy the customer approved in the wallet. No popup per request.
- **First use in a hold** waits for `open_hold` to reach FINAL (about 1.2 s or more).
- **One active hold per entitlement.** A second device waits, or the gateway closes the current hold early and opens a new one under the other key. The alternative, one hold per key, costs 4 × 390 B.

## B. Same-request retry, retention and replay (gateway; replaces v1 §5.4–5.5)

The `uses` table has PK `(reg_id, hold_seq, slot)` and stores `fingerprint`, state, release, output reference and receipt. The state machine is v1's.

| Request | Response | Chain |
|---|---|---|
| Same PK, same fingerprint, row retained | The stored outcome; never re-run | Settlement returns `Already` if repeated |
| Same PK, different fingerprint | **409 conflict**; never served | `E_CONFLICT` if submitted |
| `hold_seq` above the retention watermark, row missing | Not admitted unless it is the active hold and the slot is free | — |
| `hold_seq ≤ pruned_through_hold_seq[reg_id]` | **410 "outside retry window"**: not re-run, not chargeable | `E_HOLD_CLOSED` |

**Retention window:** each row is kept for `R = max(plan output retention, 7 days)` after its hold closes, then deleted. Each entitlement keeps one integer, `pruned_through_hold_seq`.

**Size:** rows ≤ uses served within R plus the 10 slots of the active hold.

**What the chain can confirm:** only the active hold (slot by slot) and the most recent closed hold (`last_hold.slots_root`). For older holds, the only truthful answer is "closed; cannot be charged again". Earlier outcomes are kept only off chain, within the window.

## C. Storage proof, period ring, pending slots and claim targets (point 5)

### C.1 Every write is one of three kinds

- **W1:** a new record, paid by a measured deposit.
- **W2:** an in-place rewrite of an existing record with the same byte length.
- **W3:** a deletion, with the deposit refunded to the recorded payer.

| W1 only | W2/W3 only (`env::storage_usage()` delta ≤ 0, asserted in unit tests) |
|---|---|
| `new` (pre-allocates rings and slots), `sponsor_shell`, `create_plan`, `appoint_operator`, `propose_sale` (deal plus party-claim slots for buyer and seller if missing) | `ft_on_transfer`, `on_payout`, `open_hold`, `settle_hold`, `release_hold`, `refund_units`, every claim method, `install_key`, `revoke_key`, `skip_hold_seq`, `set_paused`, accept, cancel, expire, `close_sale`, `abort_close`, `withdraw_profit`, `goodwill_refund`, `unregister` (W3) |

### C.2 Period ring

`periods: LookupMap<u8, Period>` has 24 entries written at `new`.

```rust
pub struct Period { yyyymm: u32, fields: [u128; 9] }
fn book(f) {
    let i = (months_since_1970(now) % 24) as u8;
    let mut p = periods[i];
    if p.yyyymm != now_yyyymm { p = Period{ yyyymm: now_yyyymm, fields: [0; 9] } }
    f(&mut p);
    periods[i] = p;   // W2
}
```

On chain the history covers 24 months; older months exist only in events. Callbacks and settlement crossing a month boundary rewrite the record in place, so storage doesn't grow.

### C.3 Pending payouts become explicit, pre-allocated slots (this also serves point 6)

```rust
pending: LookupMap<u8, PendingSlot>            // 16 entries written at new()
pub struct PendingSlot { in_use: bool, orphaned: bool, kind: u8, amount: u128, started_at_ms: u64,
                         to: FixedAccount, plan_id: u32, reg_id: u64 /* 0 for a party */ }
enum Beneficiary { Customer{account, plan_id, reg_id}, Party{account} }
```

- **Starting a payout:** take a free slot (none free → `E_BUSY`); per-entitlement `pending_refunds ≤ 2`; `pending_total += a`. The promise callback receives `on_payout(slot_id, copy)`.
- **Callback:** the slot must be in use and equal the copy. Otherwise log and return, never panic.
- **Success:** `held −= a`; record in the period ring; free the slot.
- **Failure, customer:** if record `(account, plan_id)` exists with `reg_id` equal: `ent.claim += a`, decrement `pending_refunds`, free the slot. Otherwise (impossible while `unregister` requires `pending_refunds = 0`; defensive only): mark the slot `orphaned` and keep it occupied. `claim_orphan(slot)` by the beneficiary pays it.
- **Failure, party:** `party_claims[to] += a`. The slot is guaranteed to exist: every owner got one at `new` or at the `propose_sale` that made them buyer.
- **Claim methods name their target:** `claim_customer(plan_id)`, `claim_party()`, `claim_orphan(slot)`. No method scans entitlements.
- **Party slots** are released (W3) only by `release_party_slot()`, when the claim is 0 and the account is neither the owner nor a party to the live deal.

### C.4 Resource table (changes to v1)

- 16 pending slots (about 2 KB) and 24 period records (about 3.6 KB), both funded at `new`.
- An 8-entry deal-outcome ring (§E), funded at `new`.
- `settle_hold`: ≤ 10 ed25519 verifications plus ≤ 10 rewrites of 32 B. `open_hold`: one verification.
- Gas per verification is **not documented** on the pages I read (inferred); S2 measures it. Target worst case ≤ 150 Tgas. The protocol maximum is 1 PGas per transaction (verified).

## D. Physical token balance: the asynchronous boundary (point 6)

The review is right, and it missed the incoming direction too. All quantities below are read **at one block B**, using `block_id = B` for both the business's views and `ft_balance_of` on the token. Views at a given block are supported.

- `D_B` = payouts already debited by the token whose `on_payout` hasn't run yet; `0 ≤ D_B ≤ pending_total_B`.
- `I_B` = `ft_transfer_call` amounts credited by the token whose `ft_on_transfer` or `ft_resolve_transfer` hasn't finished; `I_B ≥ 0`.
- `S_B` = stray plain transfers, never recorded in any bucket; `S_B ≥ 0`.

**Exact relation:** `ft_balance_B = held_B − D_B + I_B + S_B`.

**Guaranteed bound at every block:** `ft_balance_B ≥ held_B − pending_total_B`.

**Equality** holds only at quiescence: no pending slot in use, no incoming transfer in flight, no strays. Then `ft_balance == held`.

**Coverage:** every payout not yet debited is covered by the balance: `ft_balance_B − I_B − S_B ≥ held_B − D_B ≥ pending_total_B − D_B`, because all buckets are non-negative.

**A callback that never runs** leaves its slot `in_use` forever. It is still counted in `pending_total`, the bound still holds, and `get_pending()` lists it. It is resolved off chain from the token's transaction outcome. There is no on-chain resolve method.

The internal bucket equation I1 is unchanged and checked after every method.

## E. Ordering control state without deleted records (point 7)

**`control_seq: u64`** increases by exactly 1 on: propose, revise, fund, unfund, accept, entering Closing, cancel, expire, `close_sale`, abort, appoint or revoke operator, plan create, sales-close or sunset. It never changes for customer or metering operations.

```rust
pub struct ControlView { business, owner, generation: u32, control_seq: u64,
  live_deal: Option<LiveDeal{ seq, version, state, digest, freeze_epoch, closing_started_ms, deadline_ms }>,
  outcomes: [DealOutcome; 8] }  // ring: { deal_seq, version, digest, status, freeze_epoch, generation_after, control_seq_at }
```

### Contract invariants (unit-tested)

- **D1:** at most one live deal.
- **D2:** a deal enters `Closing` at most once and leaves only through `close_sale` or `abort_close`. No revise or cancel in Closing.
- **D3:** in Managed mode, `generation` increases only through `close_sale` of the live Closing deal.

### Runtime rule

Apply an observation only if `control_seq > stored`. Equal means identical, so ignore it. The block height is stored as evidence, not as the ordering key.

Given a stored freeze `(X, epoch E, cs_k)` and an observation with `cs > cs_k`:

| Observation | Meaning (derived from D1–D3) |
|---|---|
| `live.seq == X` and still Closing | Still Closing |
| Generation unchanged, live deal absent or `live.seq ≠ X` | X ended without closing: aborted or expired. Unfreeze. |
| Generation increased by 1 | X closed; owner from the view |
| Generation increased by more than 1 | X closed; the current owner applies; intermediate deals marked `reconciliation_needed` |

The outcome ring is for evidence and UX only. Recovery never needs a deleted deal record.

**Legacy v2** (no counter; deals never deleted): order within each deal by `(version, status rank)`; across deals, only `generation` matters, and v2 has no freeze.

## F. Recovery after startup, restore and with replicas (point 8)

### F.1 Removing the transferable readiness signature

`Managed { metering_account, closer_account }`; `attestor` and `registry_account` are dropped.

```
close_sale(deal_seq, version, digest, freeze_epoch, closing_control_seq, service_manifest,
           drained_admin_seq, issued_at_ms)
```

Guards:
- `predecessor == closer_account`;
- `issued_at_ms ≥ closing_started_ms` and `now − issued_at_ms ≤ 20 min` (block time);
- `now < deadline`;
- every field matches the live Closing deal and `required_service_manifest`;
- v1's floor and escrow checks.

The only "readiness" is now a transaction from the closer account. The closer account holds a function-call key per business (receiver = business, methods `[close_sale, observe_control]`, no deposit; this permission model is verified). Once the deal leaves Closing, or 20 minutes of block time pass, a leaked signed transaction is useless. The fixed rule replaces registry rotation of an attestor key; the trust level is the same and is stated in §G.

### F.2 Durable runtime state

```
runtime_boot(boot_epoch)                         -- each process start: BEGIN IMMEDIATE; boot_epoch += 1
authority(business_id, control_seq, generation, owner, freeze_*, anchored_boot_epoch, anchor_block)
closer_log(business_id, deal_seq, freeze_epoch, issued_at_ms, tx_hash)  UNIQUE(business_id, deal_seq, freeze_epoch)
```

**Admin fence**, inside every admin commit transaction:

```sql
authority.anchored_boot_epoch = (SELECT boot_epoch FROM runtime_boot)
AND freeze_state = 'none' AND owner = ? AND generation = ?
```

### F.3 Transitions (replacing T0–T6)

| # | Trigger | Effect |
|---|---|---|
| Q0 | Any process start, including after a restore | `boot_epoch += 1` ⇒ every business **quarantined** for admin. Customer paths are unaffected. |
| R1 | First admin request for B in this boot (lazy, at most one in flight per business), or a deal event | Runtime sends transaction `observe_control()` (a change method with no state change; it returns ControlView) from its observer key and waits for `FINAL`. The transaction references a recent block hash and a fresh nonce, so its execution, and the state it returns, comes **after** the request was made. A stale node cannot produce this outcome; it times out and B stays quarantined. |
| R2 | R1 outcome | Compare-and-set `control_seq`, regardless of what the (possibly rolled-back) DB holds, since the anchored view is newer. Live Closing ⇒ freeze, then **drain again in this boot** (fences any ops a restore revived). Otherwise admin reopens for the observed owner. `anchored_boot_epoch = current`. |
| T1–T5 | v1's transitions, with the §E ordering rule | Unchanged in meaning |
| C1 | Issue a close | Requires a freeze anchored in this boot, a drain completed in this boot, and a manifest match. Insert into `closer_log` (the unique row picks one issuer), then sign and send. A duplicate after restore is harmless: the second `close_sale` fails with `E_STATE`. |

**Why this is safe.** Administration can commit only if it was anchored in the current boot by a fresh on-chain transaction outcome, and that outcome showed no Closing deal or a terminal one. A close can happen only through the closer, which itself requires a freeze and drain anchored in the current boot. A deal that enters Closing after the anchor can't close until the runtime observes and freezes it, and any administration done before that shows up as a manifest mismatch.

**Replicas.** The fence reads `boot_epoch` from the database inside the transaction, so a replica holding stale memory fails as soon as any other replica restarts. Cost: re-anchoring, bounded at one `observe_control` transaction per business per boot, sent only when needed.

**Outside this model** (stated plainly):
- the database rolled back while the process keeps running, with no restart;
- a dishonest RPC that fabricates transaction outcomes. Verifying outcomes with light-client proofs would remove this trust and is a later option.

## G. Corrected language and the exact limits of trusting the runtime (point 9)

### Corrected language

- **Business records that transfer:** studio conversation and work logs, build events, revisions, releases, evaluations and use records. Personal notes are **not implemented**. The seller is told before listing that this history transfers. No claim that "chats stay with the seller".
- **Plan terms and service contracts are public by design.** A salt doesn't make a published document private. Salted digests protect only documents that aren't published (deal terms shared between the two parties). The fingerprint salt is held by the client and the gateway; it stops dictionary matching only against the on-chain fingerprint.
- **Runtime assertions, not on-chain guarantees:** release compatibility, provider, model and config identity, result quality, delivery, drain completeness and the truth of the manifest.

### The runtime (platform) **can**, if compromised or dishonest

- Settle customer-signed uses it never served: up to what the customer signed (≤ 10 per hold, ≤ the key's daily cap).
- In browser mode, sign uses itself, because platform-served code holds the use-key. Exposure is bounded by the key policy the customer approved in their wallet. Non-extractable WebCrypto keys reduce exfiltration but not misuse. SDK keys held outside platform code are stronger.
- Close a deal both parties accepted, within its deadline, without draining, or with a false manifest.
- Refuse service or refuse to close (leading to abort); keep or leak customer content it stores.
- In local preview it holds people's full-access keys, so **none** of the customer-consent guarantees hold against the platform there. This must be labelled.

### The runtime **cannot**

- Charge a use without a valid customer signature, charge it twice, or charge more than the plan's price.
- Make a hold without a customer-signed HoldAuth.
- Move money backing unconsumed units into `available`.
- Change price, floor, grants, terms or digest, or close a deal that wasn't accepted.
- Redirect payouts or claims, or withdraw treasury.
- Block refunds or claims: these are on-chain methods the customer calls directly.

## H. Where a guarantee isn't achievable under this model, and the alternatives

| Wanted | Not achievable here because | Alternative (cost) |
|---|---|---|
| Proof of delivery | The contract can't observe a service performed off chain | Plan option "ack-required": settle only uses the customer signed *after* receiving output. The business takes the risk of clients going offline. Later slice. |
| A conflict-checked history beyond the active and previous hold | Bounded storage | Fingerprint ring per key: W × 40 B per key |
| Freshness without trusting the RPC | Needs proof verification | Light-client proofs (`EXPERIMENTAL_light_client_proof`); out of scope |
| Concurrent holds on several devices | One hold per entitlement | One hold per key: +1.2 KB per entitlement |
| Charging uses served when the gateway was down past `settle_until` | Customer protection takes priority | None; this is a disclosed revenue risk |
