# Astra review of the transfer amendment

Candidate: `2026-11-02_003d-revision2.md`. Still design analysis, no contract implementation
accepted or deployed. The hold-bound signatures, unique registration IDs and explicit
runtime trust limits substantially improve the candidate. Do not convert its "coherent"
conclusion into acceptance without resolving the following.

1. **Pending payout storage lifetime.** C.3 allows a former party to release its zero-claim
   slot once it is neither owner nor a live-deal party. It does not exclude an in-flight
   payout. Reproduce on paper: seller withdraws → sale closes → seller deletes its empty
   party slot → FT transfer fails → callback must create/rewrite the now-missing claim slot.
   This breaks the no-allocation callback proof or loses the fixed beneficiary claim. Track
   pending counts by beneficiary and forbid deletion until all references settle; include
   pending orphan/retry paths. Do not rely solely on the current owner's slot existing.
2. **Contradictory surviving gateway rules.** The amendment says it replaces v1 section 5
   where conflicting, but retains gateway references to nonce watermarks and standalone
   not_after. Produce one consolidated candidate with hold/slot identity throughout:
   request admission, provider deadline, settlement outbox, result retention, closed-hold
   readback and exact unknown-outcome UI. A closed hold cannot return per-slot Already;
   specify how an unknown close/settlement response is reconciled with last_hold and the
   gateway's persisted batch without guessing that every use charged.
3. **Startup and close issuance recovery.** Define the crash between the unique closer_log
   insert and signing/sending, and the unknown transaction outcome. What exact state permits
   continuation/retry? A uniqueness row must not wedge Closing until abort, nor authorize
   blind reissue under a changed manifest. A future issued_at must be explicitly rejected,
   not left to subtraction behavior. Bind all generation/deal fields unambiguously.
4. **Source and guarantees.** F.1's account/key layout, R1's transaction freshness and the
   claimed gas/storage parameters need primary-source verification before implementation.
   A fresh transaction sent to an honest-but-lagging RPC is useful, but the complete proof
   must include observation after concurrent close/abort, current boot fencing at the actual
   admin commit, and re-draining restored operations. List availability costs and failure
   modes separately from safety. Same-process DB rollback remains explicitly out of scope;
   operational recovery must detect or forbid it, not accidentally permit that workflow.

One active hold, maximum ten units, and daily key limits are initial engineering choices,
not Tony's finalized product policy. Keep configurable validated bounds and describe the
multi-device/latency tradeoff. Acceptance for an implementation slice should name the exact
subset proved, with remaining gas/sandbox/runtime integration evidence left open.
