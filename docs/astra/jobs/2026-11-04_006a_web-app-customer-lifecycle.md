## Grounded gap

002e's design explicitly excludes customer release of web_app_bundle/1. Today's releases.ts
is tied to ManagedRuntime.artifact and extraction evaluation currency; customerUse.ts executes
text extraction and reads artifact.spec.input.max_chars. A Studio preview alone therefore
does not give the second product family a customer lifecycle. Do not just route bundles into
the extraction interpreter or label an owner preview a released product.

## What people can do

A founder takes a checked fictional digital-service estimator from Studio, reviews its
customer behavior and limitations, and deliberately releases an immutable version. Its
published business profile opens the actual customer app. The founder can create and test an
update without changing the active customer product; release, withdrawal and rollback are
explicit. After acquisition the buyer manages the same product and customer address, the
seller loses administration, and existing customer commitments continue.

Use digital-business content and fictional rates. Keep the first supported browser app
honest about its client-side calculations, lack of payment processing and absent backend.
Do not fabricate paid use, compute cost, revenue, successful isolation or hosted availability.
Local app operation is reviewable before any separately authorized public hosting/release.

## Underneath

1. Design an explicit product-kind release/admission model before coding. Preserve extraction
   release identities, existing customers and100/20/80. A new family needs its own meaningful
   readiness policy: exact bundle digest, real check evidence, supported behavior, isolation/
   browser limitations, dependencies and versioned customer terms. Missing actual engine
   evidence must not be converted into a passed release gate by a test double.
2. Build durable immutable release records, explicit activation/retirement/rollback, owner
   epoch fences, idempotent recovery and normal-app composition. No generated code executes
   inside the platform host. Keep the separate preview/customer serving boundary and bounded
   capability URLs; distinguish owner preview authority from customer release access.
3. Make the real released UI usable from the public product profile and a customer workspace.
   Client-only computation cannot produce trustworthy server-metered usage merely by posting
   a browser success message. Define actual access/charging semantics for this family; never
   silently decrement extraction units or represent client-reported work as verified service.
   Free access can be an explicit supported offer, not a stand-in for an implemented paid plan.
   Any paid access extension needs enforceable admission and equivalent customer-rights tests.
4. A release switch pins already-admitted work to its agreed version where applicable. An
   owner must not silently replace promised behavior or erase customer state/history to make
   an update pass. Define rollback/withdrawal and unsupported recovery behavior plainly.
5. Sale changes administrative authority, not the customer's product identity. Include this
   family in actual business reconciliation and evidence: what's transferred, which runtime
   and external dependencies remain, version, customer obligations and operating instructions.
   Private founder conversations and unrelated credentials are never sale assets.
6. Do not add arbitrary external network access, package execution, fake backend endpoints or
   silent credential sharing to make a sample work. Implement further capability as separately
   reviewed bounded adapters. Preserve the broader platform roadmap rather than rebranding
   a pure calculator as all SaaS, AI-agent and portal support.
