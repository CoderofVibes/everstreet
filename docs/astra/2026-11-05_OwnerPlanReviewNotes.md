This is virtual clock advancement at an existing deterministic writer barrier, not a measured real-network latency claim. Execution correctly refuses unsafe work; the design must address admission/readiness and a useful customer recovery, without weakening that refusal.

## Requirements for reviewing Phase A

The proposed compatibility function must distinguish the contract's structural validity, enough time to review/sign/submit, and enough time for actual configured execution plus margin. Account for the interval left when authorization is submitted near its permitted deadline, rather than validating only an immediate confirm. Include meaningful signing/review time in guided defaults. Do not shrink existing safety margins or silently alter immutable existing plans. Evaluate whether a plan with a supported wider window is enough, or the envelope's permitted latest signing time must also account for execution requirements; ground the decision in actual timeLeft/dispatch rules.

Reuse one compatibility policy across guided creation, existing-plan inspection/offer creation, customer prepare and execution readiness where appropriate. Runtime configuration changes can invalidate previous compatibility: a cached review cannot make an old offer permanently usable. Keep existing plan contents visible with an actionable reason; never present a published-but-unusable offer as ready. Preserve precise clock freshness, block/local-time relationship and fail-closed behavior.

Phase B needs durable regression cases for the reproduced boundaries and a supported non-default runtime, plus a late-but-permitted confirmation path proving the intended customer behavior. At each refusal assert no unwanted provider invocation, charge, additional hold or duplicate creation, and verify any already-reserved unit follows the established recovery path. Existing tests should be reused where they prove the exact claim, not replaced with assertions mirroring a new helper.

## Phase-A draft review: separate safe submission from contract expiry

Reviewed the initial OWNER_PLAN_SETUP draft while70487 is still live. The new servePolicy correctly recognizes the late-signing issue, but section5 proposes `accept_by = serve_until - reserve`. **Do not implement that assignment into the existing accept_by_ms field.** It has a different meaning today: the actual last block time when the signed contract hold can still open (`serve_until - MIN_SERVE_MS`). `decideReservation` row7 uses it to prove expired_unopened; other recovery/allocation code relies on that proof. The contract's open_hold has no new reserve argument and still accepts through the60second boundary. A platform execution target cannot shorten a signed authorization's on-chain lifetime.

Independent finite counterexample against current code: prepare an ordinary request and sign with the existing synthetic fixture key; take a copy of its ExpectedHold with the proposed accept_by shortened to serve_until-120000; advance the synthetic block500000ms into a600000ms window. Original decideReservation is pending/row8, the proposed shortened copy says refused/expired_unopened/row7, and the same original signed hold still opens through FixtureChain.openHold with actual signature verification. Final command exit0 in1.15seconds; DB closed. This is a counterexample to the proposed design, not a newly introduced production defect. An initial experiment passed env.hold without its separate key-slot/epoch fields and hit u8 range validation; the corrected run uses the original persisted authorization fields and supplies the actual evidence above.

Required correction D1: retain contract accept_by_ms = serve_until - MIN_SERVE_MS for ambiguity, expiry, sequence/allocation and recovery. Derive a distinct operational submit cutoff and earlier signing cutoff from execution reserve. After the operational cutoff, stop new/resend dispatch where appropriate, but an already-signed/submitted unknown authorization stays unknown until real contract evidence proves its outcome or impossibility. An original arriving in the interval between operational cutoff and contract expiry may reserve a hold; reconcile the original identity and return it uncharged if it cannot run. Never release its allocation, create a replacement hold or call it failed merely because the operational target passed. Exercise both lost reply and delayed original arrival in that interval.

Required correction D2: account for observed block time versus local time. The draft uses sign_by = now + signWithin while serve_until is T + window. A fresh-but-lagging block can already consume part of the advertised execution reserve. Ground absolute cutoffs in the signed serve_until and the same conservative clock semantics used by timeLeft; document permitted freshness/future skew and recheck at actual dispatch. Test a still-accepted old block and future-skew boundary, not only exactly synchronized fixture clocks. No promise that arbitrary network delay is harmless; preserve refusal and recovery.

Product decisions Q1/Q2: keep SUPPORT by default only with an explicit review showing old and resulting masks; removing it requires the deliberate choice already designed. Include older-generation SUPPORT and combined slots, not just the older METERING case. Keep the guided600000ms hold when supported, rather than the minimum300000ms: beginners need reasonable time to review and recover. Derive the real minimum from supported runtime settings; unavailable settings get a remedy rather than silently squeezed margins.

Further design clarifications before Phase B: derive the proposed settlement-grace rule from actual protection/settlement/retry deadlines instead of asserting420000ms without its timing argument; distinguish source service work from isolated build-worker requirements so an already-tested supported extraction service does not acquire an unrelated worker-installation requirement; make conflict behavior explicit when two tabs propose different plan inputs under the same control identity. Successful plan creation and historical outcome evidence remain separate from current authority/readiness after an away-and-back ownership change.
